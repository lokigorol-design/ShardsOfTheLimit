# Правила проекта для Codex

## Область работы

- Работать только внутри текущего Unity-проекта.
- Сначала читать существующие инструкции, документацию, манифест пакетов и настройки проекта.
- Сохранять пользовательские изменения и не переписывать несвязанные файлы.
- Не обновлять Unity, Render Pipeline и сторонние пакеты без отдельного решения.
- Не добавлять сетевой код, серверную часть, монетизацию и глобальную карту в боевой прототип.

## Архитектурные правила

- Данные контента хранить в `ScriptableObject`; состояние конкретного боя — в runtime-объектах, а не в ассетах.
- Не изменять `ScriptableObject` во время игры как источник текущего здоровья, перезарядок или статусов.
- Эхо игрока и противники используют общие `UnitDefinition`/`CombatUnit`; принадлежность и управление задаются отдельно.
- Чистую математику сетки, паттернов, очереди и эффектов отделять от MonoBehaviour, сцены и визуализации.
- Ссылки на определения использовать вместо копирования данных способности в каждое Эхо.
- Не создавать один гигантский класс способности с полями на все будущие эффекты.
- Новая уникальная механика может требовать нового класса эффекта; это допустимо и предпочтительнее условного «универсального конструктора».

## Границы первой версии

- Только фиксированная карта, созданная вручную.
- Только локальный одиночный бой.
- Только стандартный Inspector; собственные окна Editor — после доказанной необходимости.
- Только временная графика и простые VFX-префабы.
- Фиксированные параметры способностей и прямые характеристики Эхо.
- Тео, Оро и Фау отложены и не должны проникать в API первой версии.

## Качество изменений

- Делать небольшие, проверяемые изменения.
- После каждого завершённого среза проверять компиляцию и тесты.
- Не скрывать ошибки предупреждениями или пустыми обработчиками исключений.
- Для публичных типов и нетривиальных решений писать короткие содержательные комментарии; очевидный код не комментировать.
- Поддерживать однозначные имена без сокращений, непонятных владельцу проекта.
- Обновлять документацию, если реализация осознанно отклоняется от утверждённой архитектуры.

## Работа с Unity

- Не редактировать вручную бинарные ассеты.
- Всегда сохранять `.meta` вместе с Unity-ассетом.
- Не создавать и не коммитить `Library`, `Temp`, `Logs`, `Obj`, сборки и пользовательские настройки IDE.
- Избегать зависимости логики от поиска объектов по строковым именам и глобальных `Find` в игровом цикле.
- Не хранить ссылки на объекты сцены внутри контентных определений, если ссылка должна работать между сценами.

## Перед передачей результата

- Сообщить, что реально проверено в Unity, а что проверено только статически.
- Указать точную сцену и действия для ручной проверки.
- Перечислить известные ограничения.
- Не заявлять о готовности этапа, если не выполнены его критерии выхода.
